# MathViz 几何方向阶段性归纳与结论

**日期：2026-10-03**  
**阶段性质：方向性阶段结论，不是全题型完备性证明**

---

## 1. 背景

MathViz 前期采用了一条较重的工程路线：

```text
自然语言题目
→ Parser
→ ProblemSpec
→ Capability Registry
→ Deterministic Math Engine
→ Scene IR
→ SVG / Runtime
```

该路线的优点是数学语义可验证、执行确定、失败可控，但随着实现深入，工程复杂度快速上升。

尤其是当每一种题目结构、求解目标、运动关系、几何关系都倾向于继续扩展 capability 时，系统逐渐表现出以下问题：

- 为大量并不值得动画化的简单数学题建设专用能力；
- 为追求覆盖率和严格正确性投入过多工程成本；
- 大模型的数学理解、代码生成和教学设计能力没有被充分利用；
- 系统容易从“数学可视化生产工具”演化为“形式化数学编译系统”；
- 从约 90% 能力继续追求 99% 甚至更高可靠性的边际成本过高。

因此，本阶段重新提出并实际测试了一条更轻的路线：

> **让强模型直接理解数学题，并直接生成具有教学价值的交互式 SVG 页面；系统只提供薄运行、验证和必要的一次 repair。**

---

# 2. 新路线的核心假设

新的核心假设不是：

> 大模型能够解决所有数学题。

而是：

> **对于那些“动态变化本身能够帮助学生理解数学结构”的题目，强模型有能力直接完成数学理解、参数化、交互设计和 SVG 实现，不必预先为每一种题型建立 capability。**

这类题通常具有以下特征：

- 动点；
- 参数变化；
- 几何对象联动；
- 条件变化导致结论变化；
- 极值、边界、临界状态；
- 取值范围；
- 充分必要条件；
- 固定部分条件后观察其他条件如何变化；
- 一个静态结论实际是更大连续状态空间中的特殊位置。

相反，类似简单匀速运动、直接代数计算等题目，即使可以动画化，也未必具有足够的教学价值，因此没有必要为了“全覆盖”而建设。

---

# 3. 四次 SVG 几何实验

## 3.1 Spike 01：圆与线段交点的取值范围

核心结构：

- 正方形；
- 动点 P；
- 以 P 为圆心、PB 为半径的圆；
- 研究圆与对角线 AC 有两个不同公共点时参数的范围。

模型直接完成了：

- 动点控制；
- 圆半径联动；
- 圆与直线真实交点计算；
- 线段内 / 延长线上的交点区分；
- 临界相切状态；
- 端点边界状态；
- slider / play；
- 结果延迟揭示。

实验说明：

> 大模型可以直接处理“动态交点 + 临界边界 + 取值范围”类型的几何可视化，不需要为该题型建立专用 capability。

---

## 3.2 Spike 02：直角三角形内接矩形面积极值

核心结构：

- 点 P 沿斜边移动；
- 矩形随 P 连续变化；
- 面积 S 随位置连续变化；
- 存在内部最大值。

该实验减少了对模型的施工指导。

模型能够自行围绕面积变化组织交互，并正确找到极值结构。

实验说明：

> 模型不仅能够把已有几何变量“画出来”，还能够主动围绕目标量组织动态表达。

---

## 3.3 Spike 03：双动点乘积约束与长度极值

核心条件：

\[
AP\cdot AQ=9
\]

模型自行完成：

- 选择 AP 为自变量；
- 推导 \(AQ=9/AP\)；
- 可行域推导；
- P、Q 联动；
- PQ 实时计算；
- 长度曲线；
- 最小值识别；
- 两个对称最大值；
- AP/AQ 交换实验；
- 探索与结论分离。

尤其值得注意的是，模型主动增加了：

> `AP ↔ AQ` 交换实验。

这不是题目要求，而是模型为了揭示对称性主动设计的教学交互。

实验说明：

> 模型已经能够处理“多对象约束联动 + 非线性关系 + 极值 + 对称性 + 教学交互设计”。

---

## 3.4 Spike 04：静态证明题的条件松弛与充分必要关系

原始静态题：

- \(BC=8\)；
- M 为 BC 中点；
- \(AM=4\)；
- 证明 \(\angle BAC=90^\circ\)。

本次不是简单把证明过程动画化，而是给模型一个教学方向：

> 尝试放松一个关键条件，使原来的固定结论变成连续变化的状态。

模型自行选择松开：

\[
AM=4
\]

保留：

- BC 固定；
- M 始终为中点。

随后模型自行构造出：

```text
AM < 4   → ∠A > 90°
AM = 4   → ∠A = 90°
AM > 4   → ∠A < 90°
```

并进一步发现：

- \(AM=4\) 对应一条临界圆；
- 圆内、圆上、圆外分别对应钝角、直角、锐角；
- 原题的 90° 不是孤立结论，而是连续状态空间中的临界边界；
- 直角位置不是一个点，而是一整条轨迹；
- 原命题可以扩展为充分必要关系。

交互上，模型自行设计了：

- A 二维自由拖动；
- 径向 slider；
- 回到原题状态；
- 显示临界圆；
- 沿射线扫描；
- 隐藏推广结论；
- 实时角度与长度计算。

实验说明：

> 模型不仅能够执行已有动态题，还能够在指导性的教学目标下，把一个静态命题重新组织为连续参数空间，并发现更一般的数学结构。

---

# 4. 当前阶段性结论

## 4.1 已经得到较强支持的结论

基于上述四次实验，目前可以较有信心地认为：

> **对于适合通过动态变化来理解的中学二维几何题，强模型已经具备直接完成数学理解、交互设计和 SVG 实现的能力。**

至少已经覆盖了以下能力形态：

```text
动态交点
临界状态
取值范围
面积极值
双变量联动
非线性约束
对称性
连续参数变化
静态条件松弛
轨迹发现
充分必要关系
区域分类
探索式教学设计
```

因此，目前没有证据支持继续采用以下假设：

> 每一种此类几何题都必须预先建立一个专用 capability，模型才能可靠生成动画。

相反，四次实验均支持：

```text
强模型
→ 直接理解题目
→ 自行参数化
→ 自行选择交互方式
→ 自行生成 SVG / JS
→ 浏览器运行
```

作为主路径。

---

## 4.2 这不等于“完全让模型自主”

本阶段另一个重要结论是：

> **生产系统不需要追求“完全零提示自主”。**

提示词本身就是产品设计的一部分。

在实际生产中，用户、教师或产品可能明确希望：

- 强调某个条件；
- 松开某个条件；
- 展示充分必要关系；
- 不要直接给答案；
- 先让学生探索；
- 突出临界状态；
- 比较两个构型；
- 增加函数图像；
- 增加某种操作方式；
- 改变教学顺序；
- 强调某个新发现。

这些都完全可以进入提示词。

因此，更合理的目标不是：

> “模型必须什么都自己想到。”

而是：

> **给模型题目 + 教学意图 / 演示要求，模型能够直接把它实现为高质量的动态可视化。**

提示词是高层教学导演指令，不是底层题型 capability。

---

# 5. 对 Capability 路线的重新定位

Capability 不应再作为 MathViz 几何主路径。

原主路径：

```text
题目
→ Parser
→ Capability
→ Deterministic Engine
→ Scene IR
→ SVG
```

建议调整为：

```text
题目
+ 教学意图
        ↓
强模型
        ↓
数学理解
参数化 / 条件松弛
教学设计
交互设计
        ↓
HTML + SVG + JavaScript
        ↓
浏览器运行
        ↓
薄验证
        ↓
必要时一次 repair
```

以前已经完成的能力不需要删除。

例如：

- Geometry DSL；
- 数学 helper；
- Function2D；
- SymPy；
- Runtime；
- stateAt(t)；
- SVG helper；
- deterministic solver。

它们可以降级为：

```text
optional helper
optional verifier
optional fallback
```

即：

> 模型需要时可以调用，但不再要求所有题都经过这套系统。

---

# 6. 薄验证层是下一步真正值得建设的系统能力

四次实验表明，主问题已经不再是：

> “怎样预先描述所有数学题？”

而是：

> “怎样便宜地判断模型生成的页面是否可用？”

因此，下一阶段最值得建设的是通用薄验证层。

## 6.1 运行检查

检查：

- HTML 是否能直接运行；
- console error；
- runtime exception；
- NaN；
- Infinity；
- 非有限 SVG 坐标；
- 页面崩坏。

---

## 6.2 参数扫描

对于 slider、动点、参数等：

```text
参数区间
→ 自动采样
→ 检查状态
```

重点检查：

- 连续性；
- 是否突然跳变；
- 是否出现非法几何；
- 是否有异常值；
- 临界附近是否稳定。

不需要每题建立形式化证明。

---

## 6.3 数学抽查

只检查高价值点：

- 边界；
- 临界状态；
- 极值；
- 随机状态；
- 模型声称的推广结论。

可以结合：

- 解析计算；
- 数值计算；
- SymPy；
- 几何 helper；
- 第二模型 review。

目标是发现明显错误，而不是证明所有状态绝对正确。

---

## 6.4 视觉检查

通过截图检查：

- 图形是否被裁切；
- 标签是否重叠；
- 控件是否完整；
- 关键对象是否清楚；
- 动画状态是否具有可读性。

---

## 6.5 教学检查

这是实验中出现的新问题，也是非常重要的一层：

- 是否过早透露最终答案；
- 是否在探索前直接说出最大值 / 最小值；
- 操作是否真正对应数学变量；
- 图形有没有造成错误暗示；
- 动画是否真的帮助理解，而不是只有视觉效果；
- 是否明确区分“观察”“猜想”“验证”“结论”。

Spike 03 和 Spike 04 的 repair 都主要发生在这一层，而不是数学计算层。

这是一个很重要的生产信号：

> **未来系统的主要 repair 很可能更多是教学呈现 repair，而不是底层数学 repair。**

---

# 7. 对提示词体系的建议

未来不建议建立大量题型 prompt。

更适合建立少量“教学意图 prompt primitives”。

例如：

### 动态探索

> 将题目转化成学生可以主动探索的动态图形，不要只演示解题过程。

### 条件松弛

> 尝试固定部分条件并连续改变一个关键条件，观察结论怎样变化。

### 临界状态

> 突出展示结论发生性质变化的临界位置。

### 充分必要关系

> 如果原题条件和结论存在更一般的等价关系，尝试通过动态变化展示。

### 极值 / 范围

> 让学生通过连续变化观察目标量的范围、边界和极值，而不是一开始直接显示答案。

### 探索优先

> 在学生完成观察前，不直接泄露最终推广结论。

这些不是 capability。

它们是：

> **教学导演语言。**

模型仍然自行负责数学实现。

---

# 8. 对“什么题值得做动画”的重新定义

MathViz 不应试图动画化所有数学题。

优先选择：

### 高价值类型

- 动点；
- 图形连续变化；
- 参数变化；
- 取值范围；
- 极值；
- 临界条件；
- 轨迹；
- 相交数量变化；
- 固定部分充分条件后观察剩余自由度；
- 静态证明背后的连续结构；
- 一个等式条件对应一个几何 locus；
- 离散分类背后的连续边界；
- 多条件联动。

### 低优先级类型

- 简单代数代入；
- 单步计算；
- 很容易通过静态图说明的问题；
- 单纯匀速运动；
- 动画不增加理解价值的题目。

判断标准应当是：

> **动态图是否能揭示静态文字或静态图难以直观看到的结构。**

而不是：

> 这道题能不能做动画。

---

# 9. 当前建议的几何产品模式

现阶段推荐的生产模式为：

```text
用户题目
+
可选教学意图
        ↓
GPT-5.6 Sol 等强模型
        ↓
直接生成
HTML + SVG + JavaScript
        ↓
浏览器执行
        ↓
自动薄验证
├─ runtime
├─ numerical sweep
├─ critical spot checks
├─ screenshot
└─ teaching leak check
        ↓
若有明显问题
        ↓
一次集中 repair
        ↓
最终交互页面
```

特点：

- 不追求所有题 100% 成功；
- 不提前建设所有题型；
- 不为低价值题增加 capability；
- 不建立复杂 benchmark / freeze / authority 流程；
- 失败可以 fail-closed；
- 真正出现高频失败后再决定是否建设 helper。

---

# 10. 对现有 MathViz 工作的处理

前期工作并非无价值。

保留价值较高的部分包括：

- SVG / Runtime 基础；
- 浏览器 parity；
- stateAt(t) 思想；
- seek / play / pause；
- Geometry helper；
- Function helper；
- SymPy；
- fail-closed 边界；
- testing infrastructure。

但 Parser / Capability / formal verification 不应再继续无限扩张。

建议：

```text
现有严格系统
→ 从“主生成路径”
→ 降级为“验证 / helper / fallback infrastructure”
```

这样既不浪费已有投入，也避免继续被原架构锁定。

---

# 11. 当前尚未证明的事情

需要明确保留边界。

四次实验并不能证明：

- 任意几何题都可以一次生成成功；
- 所有证明题都适合动态化；
- 复杂竞赛几何同样稳定；
- 三维几何已经解决；
- 模型永远不会数学出错；
- 无需任何 review；
- SVG 是所有教学内容的最佳形式。

目前真正可以下的结论只是：

> **对于本阶段测试的、适合通过连续变化揭示结构的二维几何题，强模型直接生成交互式 SVG 的路线表现非常好，已经足以支持将其作为下一阶段主方向。**

# 12. 阶段性决策

## 几何方向

```text
LLM-native interactive SVG
PRIMARY PATH
```

## 预定义题型 capability

```text
NO LONGER PRIMARY
```

## 强模型角色

```text
数学理解
参数化
条件松弛
推广发现
教学设计
交互设计
代码生成
```

## 系统角色

```text
运行
验证
截图检查
数值扫描
错误捕获
一次 repair
通用 helper
```

## Prompt 角色

```text
允许并鼓励表达教学意图与新的演示需求
不要求完全自主
不承担底层数学题型编码
```

# 13. 最终阶段性结论

当前最重要的阶段性结论可以压缩成三句话：

> **第一，至少在目前测试的高价值二维动态几何题上，强模型已经具备直接从题目生成高质量交互 SVG 的能力，不需要预定义题型 capability。**

> **第二，生产系统没有必要追求模型完全自主。题目之外加入“想让学生看到什么、希望怎样探索、希望放松哪个条件”等教学意图，是合理且有价值的产品输入，而不是架构失败。**

> **第三，MathViz 下一阶段不应继续扩大 capability 覆盖，而应围绕“强模型直接生成 + 通用薄验证 + 一次 repair”建设生产链，并把已有严格数学引擎降级为可选 helper / verifier。**

因此，当前几何方向的目标已经从：

> **建立一套覆盖几何题型的数学动画引擎**

调整为：

> **让强模型把适合动态理解的静态数学问题，直接转化成可探索的动态数学世界。**

这应作为 MathViz 几何方向下一阶段的主设计原则。
